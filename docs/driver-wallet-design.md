# تصميم محفظة السائق ونظام التحصيل — ZadGo

> **الحالة:** مُصمَّم وغير مُنفَّذ بعد. هذه الوثيقة مرجع كامل يكفي أي شخص
> (مطوّر أو مساعد آخر) لتنفيذ النظام دون الرجوع لمحادثة سابقة.
>
> **آخر تحديث:** بعد commit `bc95409` · إصدار التطبيق `4.0.0+1`
> **الفرع المرجعي:** `copilot/split-customer-app`

---

## 1) الخلاصة التنفيذية

نموذج محفظة السائق الحالي **مقلوب بالنسبة للطلبات النقدية**: الكود يسجّل أن
التطبيق مدين للسائق بأجرة التوصيل، بينما الواقع أن السائق يقبض كامل المبلغ
نقداً من العميل فيصبح **مديناً للتطبيق** بقيمة الوجبة ورسم التطبيق.

لا يوجد خلل مالي فعلي بعد لأن لا طلبات حقيقية، لكنه **مانع تشغيل** يجب حلّه
قبل أول طلب نقدي حقيقي.

## 3) الحساب الصحيح

### مثال: وجبة 40 ر.س · مسافة 9 كم

| البند | المبلغ | لمن |
|-------|--------|-----|
| الوجبات | 40.00 | المطعم (ناقصاً 15% عمولة) |
| التوصيل | 11.00 | السائق |
| رسم ثابت | 3.00 | التطبيق |
| **يدفع العميل** | **54.00** | |

**دفع نقدي:** السائق يقبض 54، يحتفظ بـ11، **يدين بـ43** (40 + 3).
**دفع إلكتروني:** التطبيق يقبض 54، **يدين للسائق بـ11**. السائق بلا ذمّة.

### القاعدة
```
نقدي     : الرصيد −= (itemsTotal + appShare)
إلكتروني : الرصيد += driverShare
إيداع    : الرصيد += المبلغ المُسلَّم
صرف      : الرصيد −= المبلغ المصروف
```
**الإشارة:** موجب = التطبيق مدين للسائق · سالب = السائق مدين للتطبيق.

## 4) لماذا سقف 50 ر.س غير عملي كإيقاف

طلب واحد بوجبة 40 ر.س ينتج دَيناً 43 ر.س — أي أن السقف يُستنفد بعد **طلب
واحد**.

**السقف الصحيح ≈ متوسط الدَّين للطلب × عدد الطلبات بين التحصيلين.**
تحصيل يومي × 10 طلبات ≈ 400–500 ر.س.

**القرار المعتمد:** 50 ر.س تبقى **عتبة تنبيه**، والسقف النهائي يُحدَّد من
بيانات التشغيل الفعلية في المرحلة ١.

## 5) الخطة المرحلية

### المرحلة ٠ — التجريب (المعتمدة الآن)
- الدفتر **يسجّل كل الحركات** بصمت.
- **لا تقييد إطلاقاً**: كل السائقين يستلمون كل الطلبات.
- **المحاسبة يدوية** خارج التطبيق.
- الإدارة ترى أرصدة السائقين وسجلّ الحركات.
- الهدف: التحقّق من صحة الأرقام بطلبات حقيقية قبل أي إيقاف.

### المرحلة ١ — تشغيل محدود
- تنبيه بصري للسائق والإدارة عند تجاوز عتبة التنبيه (50 ر.س).
- تسجيل الإيداعات في التطبيق (الإدارة تسجّل استلام النقد).
- **ما زال بلا إيقاف** — تُقاس أرقام التشغيل الحقيقية.

### المرحلة ٢ — تشغيل كامل
- إيقاف إسناد الطلبات **النقدية** عند بلوغ السقف.
- **الطلبات الإلكترونية تبقى متاحة دائماً** — صمّام الأمان: السائق لا يتوقّف
  عن العمل، وأرباح الإلكتروني تُسدّد دَينه تلقائياً (نموذج Uber).
- شحن رصيد اختياري لرفع سعة السائق النقدية.

**مبدأ التصميم:** تُبنى البنية كاملة في المرحلة صفر ومفتاح الإيقاف **مطفأ**،
فالانتقال بين المراحل = تغيير إعداد لا إعادة برمجة.

## 6) حل مشكلة الطلبات كبيرة القيمة

| الطبقة | الآلية |
|--------|--------|
| **١ — سقف الطلب النقدي** ⭐ | طلب يتجاوز مبلغاً معيّناً → الدفع إلكترونياً إلزامياً. الحل المعياري: لا يُطلب من أي سائق حمل مبلغ ضخم أصلاً |
| **٢ — حدود متدرّجة** | سائق جديد سقف أقل؛ يرتفع تلقائياً مع عدد التوصيلات والتقييم |
| **٣ — شحن رصيد** | السائق الراغب بطلبات نقدية أكبر يشحن رصيداً فترتفع سعته |

## 7) ما يجب تنفيذه (المرحلة صفر)

### 7.1 النموذج — `lib/models/models.dart`
- إضافة `balance` (double, بإشارة) إلى `Driver` بجانب `pendingPayout`
  الحالي (يُبقى مؤقتاً للتوافق ثم يُزال).
- نموذج `DriverTransaction` جديد:
  `{ id, driverId, type, amount, balanceAfter, orderId?, note?, performedBy, createdAt }`
  حيث `type ∈ { deliveryCash, deliveryOnline, deposit, payout, adjustment }`.

### 7.2 الخدمة — `lib/providers/firebase_service.dart`
- تعديل `markOrderDelivered` (السطر 675) ليقرأ `order.paymentMethod`:
  - نقدي → `balance -= (itemsTotal + appShare)` + حركة `deliveryCash`
  - إلكتروني → `balance += driverShare` + حركة `deliveryOnline`
- `recordDriverDeposit(driverId, amount, note)` → `balance += amount`
- `recordDriverPayout(driverId, amount, note)` → `balance -= amount`
- `streamDriverTransactions(driverId)`
- كل عملية في **batch واحدة** (تحديث الرصيد + كتابة الحركة معاً).

### 7.3 مجموعة جديدة في Firestore
`driver_transactions` — قواعدها: قراءة للسائق صاحبها وللمدير، كتابة للمدير
والسائق (عند التوصيل) فقط. تُضاف إلى `firestore.rules`.

### 7.4 الواجهات
- **السائق** (`driver_home.dart` السطر 443): استبدال «المستحقات» برصيد
  بإشارة ونصّ واضح: «لك X ر.س» أو «عليك تسليم X ر.س» + سجلّ حركاته.
- **الإدارة**: شاشة أرصدة السائقين + أزرار **إيداع**/**صرف** + سجلّ الحركات.

### 7.5 الإعدادات (لتبديل المراحل بلا برمجة)
تُضاف إلى `Pricing` في `lib/utils/helpers.dart` أو إلى مستند
`delivery_settings/config` في Firestore:
```
driverDebtWarningThreshold = 50      // عتبة التنبيه
driverDebtHardLimit        = null    // null = بلا إيقاف (المرحلة ٠)
maxCashOrderValue          = null    // null = بلا سقف لقيمة الطلب النقدي
```

## 8) قرارات معلّقة

1. **السقف النهائي للإيقاف** (المرحلة ٢): 400 ر.س (تحصيل يومي) أم 200
   (تحصيل مرّتين يومياً) أم رقم آخر — يُحدَّد من بيانات المرحلة ١.
2. **سقف قيمة الطلب النقدي**: مُوصى به بقوة، والقيمة تُحدَّد لاحقاً.
3. **دورية التحصيل**: يومي أم عند بلوغ العتبة.

---

## 9) قيود قائمة (شفافية)

- **لا Cloud Functions**: منطق المال يُنفَّذ من أجهزة المستخدمين، وقواعد
  Firestore هي خط الدفاع الوحيد. السائق يستطيع نظرياً تعديل رصيده على مستنده
  لأن التوصيل يُنفَّذ من تطبيقه. الإغلاق الكامل يتطلّب نقل المنطق للخادم.
- **الدفع الإلكتروني غير مُنفَّذ فعلياً**: `PaymentMethod.card/wallet`
  موجودان كخيارين بلا بوابة دفع حقيقية. حتى تُنفَّذ البوابة، كل الطلبات
  عملياً نقدية.
